## 1 · Headline

The BT secondary lane refuses to load any of the 7 CAMPAIGN_002 H4
CSVs because **every instrument** simultaneously fails:

- **row-sha256 match** (computed by `data_adapter.compute_csv_sha256`);
- **raw-file sha256 match** (full-file SHA256 also drifts);
- **row count** (CSV has 9,949–9,953 rows; provenance recorded
  9,931–9,933);
- **first / last timestamps** (CSV timestamps include local-time
  offsets and a 5-day-later last bar than the provenance recorded).

The drift is uniform across all 7 instruments. This is consistent with
a single re-export run that picked up ~5 days of fresh H4 candles and
wrote timestamps in the local timezone, without re-committing the
sidecars to match.

## 3 · Worked example: EUR_USD

| field | CSV | provenance |
|---|---|---|
| `data_sha256` (row-level) | `16ed0bc40d05b578…` | `866d75446030655b…` |
| raw file sha256 | `87cd3a1301362d48…` | (n/a — provenance stores row-sha) |
| candle count | 9949 | 9931 |
| first_ts | `2020-01-01T14:00:00-08:00` | `2020-01-01T22:00:00+00:00` |
| last_ts | `2026-05-24T14:00:00-07:00` | `2026-05-19T21:00:00+00:00` |
| provenance `exported_at` | — | `2026-05-22T20:38:19+00:00` |

Note the timestamp-format difference: the CSV writes timestamps with
local-timezone offsets (`-08:00` PST in winter, `-07:00` PDT in
summer); the prior canonical export used UTC (`+00:00`). The two are
the same instant in UTC, but the row-sha256 algorithm hashes the
string representation, so the offset format alone is enough to drift
the sha.

The CSV's last_ts of `2026-05-24` is **5 days past** the provenance's
`2026-05-19`. The H4 store has been updated since the original
export.

## 4 · Root cause

Two coupled issues, both fixable in Phase 2:

1. **Timestamp serialisation drift.** The export script
   ([`scripts/export_lean_parity_data.py`](../../scripts/export_lean_parity_data.py))
   uses `Candle.time.isoformat()`. If `Candle.time` is a
   timezone-aware datetime whose tzinfo is the machine's local zone
   instead of UTC, the resulting string includes a local offset.
   When the original export ran on 2026-05-22 (apparently with a UTC
   environment), it wrote `+00:00` offsets; the re-export on
   2026-05-25 (machine in PDT/PST locally) wrote local offsets. The
   row-sha differs even when the underlying numbers do not.

2. **Lock-step missed.** The CSV was rewritten on 2026-05-25 17:50
   (mtime) but the `*.provenance.json` files were last committed on
   2026-05-22 with the older content. The export script writes both
   in the same run; whoever re-ran the export on 25 May did not
   re-commit the sidecars.

The fix in Phase 2 is to **re-export all 7 instruments in a single
run** against the canonical SQLite DB
(`data/campaign_002.sqlite3`, symlinked from main repo), which the
existing `scripts/export_lean_parity_data.py` already does — it writes
the CSV and the matching provenance sidecar back-to-back, so as long
as we run it once per instrument from the *current* DB, the
write-out is atomic at the lock-step level.
