# CAMPAIGN_002 H4 → Lean Parity Mapping Spec

**Date:** 2026-05-22 · **Branch:** `infra-lean-parity-run-001` · Phase 1

A precise mapping from the bespoke engine's CAMPAIGN_002 H4
`trend_following` baseline to a Lean re-implementation. Authored
**before** the Lean algorithm so every behavior is pinned and every
approximation is documented up front.

> Verification only. `strategy_evidence: false`. CAMPAIGN_002 is
> **REJECT** and stays REJECT; nothing here approves a strategy.

## 0. Parity scope — the RiskEngine decision (read first)

The bespoke CAMPAIGN_002 run puts every signal through the production
`RiskEngine` (`mode=backtest`): spread filter, session-blackout filter,
and loss-limit gates. That pipeline produced the committed **1,032**
trades. The `RiskEngine` is a large, separate bespoke layer; faithfully
re-implementing it in Lean would itself need parity verification —
verifying the instrument with an un-verified copy of part of the
instrument is circular.

**Decision:** the Lean parity algorithm replicates the **strategy +
engine mechanics** (indicators, signals, fills, exits, sizing) and
**not** the RiskEngine gates. The bespoke engine exposes exactly this
path — `risk_engine=None`, labelled in the source as "kept for opt-out /
parity tests". The apples-to-apples reference is therefore the
**no-RiskEngine bespoke run**:

- `research/lean_parity/campaign_002_h4_bespoke_reference.json` —
  generated by `scripts/run_custom_campaign_002_h4_parity.py
  --no-risk-engine`.

The no-RiskEngine run produces **1,647** trades — higher than 1,032
because the spread / session / loss-limit gates are not applied. **The
Lean algorithm targets 1,647, not 1,032.** The 1,032 figure is the
actual CAMPAIGN_002 result and was already reproduced exactly with the
RiskEngine wired in (`backtests/diagnostics/custom_campaign_002_h4_parity.md`).

## 1. Strategy identity

- Strategy: `trend_following`, version `0.1.0-baseline-frozen`.
- Timeframe: **H4** (OANDA H4, 17:00-New-York-aligned bars).
- Universe (seven instruments): EUR_USD, GBP_USD, USD_JPY, AUD_USD,
  USD_CAD, USD_CHF, NZD_USD.
- Source of truth: `src/forex_bot/strategies/trend_following.py`,
  `src/forex_bot/strategies/indicators.py`,
  `src/forex_bot/backtesting/engine.py`,
  `src/forex_bot/backtesting/fills.py`, `src/forex_bot/risk/sizing.py`.

## 2. Data

- Input: the exported OANDA **practice** H4 bid/ask CSVs at
  `research/lean_parity/exports/campaign_002_h4/<INST>_H4_lean.csv`
  (columns: `time,bid_open..bid_close,ask_open..ask_close,volume`).
- Window: 2020-01-01 → 2026-05-20; completed candles only.
- Consume the CSV as Lean **custom data** (`PythonData` subclass),
  preserving each candle's 17:00-NY-aligned **open** timestamp. Do not
  use Lean's native FX feed — its bar boundaries will not match.
- The bespoke engine works in **mid** prices for indicators
  (`open/high/low/close` are mid = (bid+ask)/2) and **bid/ask** for
  fills. The Lean algorithm must do the same: indicators on mid,
  fills on bid/ask.
- No synthetic fallback — real exported candles only.
- Fill timing: **`signal_bar_close`** — CAMPAIGN_002 predates the
  next-bar-open model; the entry fills at the signal bar's own close.

## 3. Indicators

All indicators consume **completed** bars and never peek ahead. Bespoke
definitions (`indicators.py`):

| indicator | bespoke definition | Lean mapping |
|---|---|---|
| EMA(50), EMA(200) | `close.ewm(span=L, adjust=False, min_periods=L)` — recursive, α = 2/(L+1), seeded at the first sample | `ExponentialMovingAverage(L)` — same α, same recursion |
| ATR(14) | Wilder: `TR.ewm(alpha=1/14, adjust=False, min_periods=14)`; `TR = max(H−L, |H−prevC|, |L−prevC|)` | `AverageTrueRange(14, MovingAverageType.Wilders)` |
| Donchian(20) high | `high.shift(1).rolling(20).max()` — max high of the **prior 20 bars, excluding the current bar** | a 20-deep `RollingWindow` of completed-bar highs, max'd — **not** Lean's `DonchianChannel` (it includes the current bar) |
| Donchian(20) low | `low.shift(1).rolling(20).min()` | rolling window of completed-bar lows, min'd |

The Lean algorithm computes Donchian manually because Lean's built-in
`DonchianChannel` includes the forming bar — using it would be a
look-ahead bug.

## 4. Entry logic

Evaluated on each **completed** H4 bar `t` (mid prices), once the strategy
warmup of 220 bars has elapsed:

1. **Trend regime:** `EMA50[t]` vs `EMA200[t]`.
2. **Breakout:**
   - **Long** if `EMA50[t] > EMA200[t]` **and** `close[t] > donchian_high[t]`
     (where `donchian_high[t] = max(high[t-20..t-1])`).
   - **Short** if `EMA50[t] < EMA200[t]` **and** `close[t] < donchian_low[t]`.
   - otherwise: no signal.
3. **Volatility floor:** `min_atr_pips` is **`{}`** (empty) for
   CAMPAIGN_002 — the ATR floor is disabled; never blocks an entry.
4. **ADX gate:** `adx_min` is **not set** for `0.1.0-baseline-frozen` —
   the ADX gate is skipped entirely.
5. **One position per instrument:** no new entry while a position in
   that instrument is open.
6. No look-ahead: the Donchian band uses bars `t-20..t-1`; the signal
   uses bar `t`'s completed close.

## 5. Exit logic

The bespoke engine checks exits on each bar **after** entry, in this
exact order (`engine.py`). `bars_held` increments by 1 each bar from the
first bar after entry.

1. **Trailing stop update (first, every bar):** with
   `trailing_stop_atr_multiple = 2.0` and the current bar's ATR:
   - long: `new_stop = bid_close − ATR×2.0`; raise the stop only if
     `new_stop > stop` (ratchet up, never down).
   - short: `new_stop = ask_close + ATR×2.0`; lower only if
     `new_stop < stop`.
2. **Exit checks, in precedence — adverse stop first:**
   - long: if `bid_low ≤ stop` → exit **at `stop`** (reason `stop`, or
     `trailing_stop` if the stop has moved from its initial level).
   - short: if `ask_high ≥ stop` → exit at `stop`.
   - **time stop:** else if `bars_held ≥ 240` → exit at `bid_close`
     (long) / `ask_close` (short), reason `time`.
   - there is **no** take-profit and **no** opposite-signal exit for
     `trend_following` (no `take_profit_price`; a position simply blocks
     new entries until it exits).
3. **End of data:** an open trade at the last bar is closed at that
   bar's `bid_close` (long) / `ask_close` (short), reason `eod`.

Initial stop (from the strategy): long `close[t] − ATR[t]×2.0`, short
`close[t] + ATR[t]×2.0`, rounded to the instrument's display precision.

**Known Lean-mechanics mismatch:** the bespoke engine fills a stop exit
**exactly at the stop price**; Lean stop-market orders fill at the stop
or worse on a gap. Treat exit price as a tolerance comparison.

## 6. Risk and sizing

- **Sizing (no-RiskEngine path, `sizing.py::size_position`):**
  - `risk_amount = nav × 0.25 / 100` (0.25% of equity).
  - `stop_distance_pips = |entry − stop| / pip_size`.
  - `pip_value_home`: if quote currency == USD → `pip_size`; if base
    currency == USD → `pip_size / mid_price`.
  - `raw_units = risk_amount / (stop_distance_pips × pip_value_home)`;
    `units = floor(raw_units)` to whole units (trade-units precision 0).
  - `nav` compounds — it is the running equity at entry time.
- **One open position per instrument**, single position at a time per
  instrument engine.
- **Account currency USD.** PnL conversion (`engine.py::_pnl`):
  `diff = exit − entry` (long) / `entry − exit` (short);
  `gross_quote = diff × units`; if quote == USD → `gross_home =
  gross_quote`; if base == USD (USD_JPY, USD_CAD, USD_CHF) →
  `gross_home = gross_quote / exit_price`.
- **RiskEngine gates — out of Lean scope** (see §0):
  - *spread filter* (`max_spread_pips`, `max_spread_to_atr_pct`) — not
    mirrored;
  - *session-blackout filter* (rollover / Friday-close / Sunday-open) —
    not mirrored;
  - *loss limits* (daily / weekly / drawdown) — not mirrored;
  - *exposure gates* — inert in the single-instrument backtest anyway.
  Because these are not mirrored, the Lean reference is the
  no-RiskEngine bespoke run (1,647 trades), not 1,032.

## 7. Cost model

- **Bid/ask-aware fills** (`fills.py::FillModel`):
  - `spread_pips = (ask − bid) / pip_size`;
  - `slip_pips = max(0.2, spread_pips × 0.5)`;
  - long entry `= ask + slip_pips×pip_size`; short entry `= bid −
    slip_pips×pip_size`.
- Base cost regime: fixed slippage **0.2 pips**, spread multiplier
  **0.5×**.
- Commission: **0**.
- **Financing: excluded** — CAMPAIGN_002 excluded it (unmodeled in both
  engines). Do not model financing/swap in Lean.

### Known unavoidable mismatch risks

- **Indicator seeding:** pandas `ewm` and Lean's smoothers seed early
  bars slightly differently; washes out well before the 220-bar warmup
  ends, but can shift the very first eligible bars.
- **Stop fill price:** bespoke fills a stop exactly at the stop; Lean
  fills at stop-or-worse.
- **signal_bar_close timing:** the bespoke engine fills at the signal
  bar's own close; Lean must emulate a same-bar-close fill (e.g. a
  market-on-close order on the custom data), which is not Lean's
  default market-order behavior.
- **Floating-point:** Decimal (bespoke) vs double (Lean) — sub-pip
  differences in fills and PnL.

## 9. Explicit non-goals

This mapping, and the algorithm built from it, will **not**:

- improve, tune, or alter any strategy rule or parameter;
- change the bespoke engine or the CAMPAIGN_002 config;
- approve any strategy or produce a trading verdict;
- run paper / demo / live, or submit any order;
- use QuantConnect cloud or any paid service.

A parity PASS corroborates the bespoke engine; a FAIL localizes a
parity-implementation bug (fixed on the Lean side) or a real engine
discrepancy (documented). CAMPAIGN_002 remains REJECT either way.
